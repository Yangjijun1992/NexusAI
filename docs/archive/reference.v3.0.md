## 0. 文档说明与设计原则

### 0.1 目标

建设一个面向 DeepSeek API 起步、可逐步扩展到多个模型供应商的智能 API 监控、请求调度、成本治理和 Agent 任务编排平台。系统应先实现可观测、可控、可恢复的基础能力，再逐步引入历史预测和 Agent 自动化开发。

### 0.2 核心原则

1. **数据边界清晰：** 只分析本平台自身发出的请求、用户授权接入的业务指标，以及供应商公开提供的服务状态信息。不得宣称可以观察或推断供应商的全局用户流量、内部队列或真实剩余配额。
2. **安全规则优先：** 任何预测、评分或 Agent 决策都不得覆盖身份验证、权限、数据分类、预算硬上限和安全策略。
3. **默认最小权限：** 服务、项目、环境、Worker 和 Agent 仅获得完成任务所需的最小权限。
4. **失败时安全降级：** 指标缺失、状态不确定、策略服务不可用或数据质量不足时，采用保守策略，不得默认判定为低压力或自动放宽限制。
5. **有限重试：** 每次重试都必须有明确原因、次数上限、时间上限和成本上限；不确定是否已产生外部副作用时，不得直接重试。
6. **人工控制关键变更：** 生产代码合并、生产部署、权限变更、数据库破坏性变更和安全策略变更默认需要人工审批。
7. **可解释、可追踪：** 每次调度决策、策略变更、Agent 工具调用和高风险操作均可审计、可追踪。
8. **分阶段交付：** MVP 不以机器学习预测、复杂多 Agent 协作或自动合并代码为前置条件。
9. **供应商行为以适配器为准：** 不假设所有 API 都具有相同的错误码、重试语义、Token 统计字段、价格或状态接口。
10. **不承诺绝对“恰好一次”：** 对外部 API、Git、Webhook 等系统，平台以幂等、去重、状态核查和 `UNKNOWN` 状态降低重复副作用风险；无法由对端配合时，不宣称实现了端到端 exactly-once。

### 0.3 术语

- **Provider：** 模型/API 服务提供商，例如 DeepSeek。
- **Provider Adapter：** 对某个服务商 API 行为进行封装的适配层。
- **Task：** 用户提交的逻辑任务。
- **Execution：** 某个 Task 的一次执行实例。
- **Attempt：** 对某个执行步骤或请求的一次尝试。
- **Worker：** 执行队列任务的工作进程。
- **Agent：** 能够调用受限工具完成分析、文档或代码任务的模型驱动执行体。
- **UNKNOWN：** 系统无法可靠确认上一次执行是否完成或是否产生外部副作用的状态。
- **预算硬上限：** 未经授权不得突破的成本限制。
- **安全失败（fail closed）：** 关键安全控制不可用时拒绝或暂停高风险操作，而不是放行。

# 1. 项目背景与目标

## 1.1 背景

在使用模型 API 和 Agent 执行开发任务时，可能出现请求限流、响应延迟波动、服务端错误、重复请求、成本不可预测、任务积压和执行状态不一致等问题。低峰期自动启动后台任务也可能与交互式请求争抢模型额度、CPU、内存、数据库、CI Runner 或人工审核资源。

因此需要统一的 API 请求入口、实时监控、预算控制、任务调度、执行隔离和审计能力。

## 1.2 产品目标

- 统一接入模型 API，并记录请求状态、延迟、Token 用量和估算成本。
- 根据实时服务指标、队列状态、任务优先级、资源容量和预算情况控制并发与排队。
- 在 429、5xx、超时、认证失败和预算不足等场景下采取不同的处理策略。
- 提供可解释的调度决策、告警、仪表盘和审计记录。
- 为后续历史基线、异常检测和高峰预测积累质量可控的数据。
- 在严格隔离的环境中逐步支持 Agent 分析、文档生成、测试生成、代码修改和 PR 创建。
- 支持任务取消、人工接管、故障恢复、配置回滚和成本对账。

## 1.3 非目标

MVP 不承诺以下能力：

- 获取 DeepSeek 或其他供应商的全局流量、内部排队长度、全局剩余容量或未公开的限流规则。
- 预测供应商真实内部负载；预测仅针对本平台观察到的服务表现和自身需求。
- 保证第三方 API 调用端到端恰好执行一次。
- 自动突破供应商配额、项目预算、数据权限或安全策略。
- 无人审批地自动合并或发布生产代码。
- 通过“启用容器”这一配置项就宣称 Agent 已获得完整安全隔离。
- 在没有数据质量评估的情况下将模型预测直接用于关键调度。

# 2. 用户、角色与权限

## 2.1 角色

| 角色 | 主要权限 | 明确禁止 |
|---|---|---|
| 平台管理员 | 管理平台级配置、角色、Provider 配置元数据、全局策略 | 默认不可读取明文密钥；高风险操作仍需审批 |
| 安全管理员 | 管理安全策略、审计规则、凭据访问策略 | 不应单独审批自己发起的高风险变更 |
| 项目管理员 | 管理本项目任务、预算、模型白名单、仓库授权 | 不得访问其他项目数据或修改全局安全边界 |
| 开发者 | 创建任务、查看授权范围内的执行结果、提交代码变更请求 | 不得读取密钥、直接发布生产代码或修改安全策略 |
| 审核者 | 审核 PR、部署或高风险操作 | 不得批准自己发起的变更 |
| 只读观察者 | 查看授权范围内的仪表盘和报表 | 不得更改配置、预算或任务状态 |
| Agent/Worker 服务身份 | 在任务授权范围内调用指定工具和 API | 不得自行提升权限、读取其他任务或访问宿主机敏感资源 |

## 2.2 权限控制要求

- 使用 RBAC，并在项目、工作区、仓库和环境维度实施授权检查。
- 所有 API 在服务端执行权限检查，不能只依赖前端隐藏按钮。
- 高风险操作需要二次确认；生产部署、权限扩大、预算上调和安全策略变更建议采用双人复核。
- 审核者不能审批自己提交的变更。
- 管理员账号启用 MFA；登录、会话、权限变更和失败访问均需审计。
- Web 管理端实施会话过期、CSRF 防护、XSS 防护、输入校验、输出编码和速率限制。
- 若未来支持多租户，租户边界必须落实到数据库查询、对象存储、队列消息、缓存键、日志查询和后台任务中，而不只是增加 `tenant_id` 字段。

# 3. 系统范围与总体架构

## 3.1 逻辑架构

```text
用户 / Web 控制台 / CLI / 外部系统
                 |
                 v
        API Gateway / AuthN / AuthZ
                 |
       +---------+----------+
       |                    |
       v                    v
  Task Service          Admin / Policy
       |                    |
       v                    v
  Task Queue <-------- Scheduler
       |              ^      |
       v              |      v
  Worker Pool      Metrics  Budget Guard
       |              ^      |
       v              |      v
  Agent Runtime    API Client / Provider Adapter
       |                     |
       v                     v
  Sandbox / Tools        Model Providers
       |
       +--> Git / CI / Approved Integrations

公共基础设施：
PostgreSQL（事务与任务状态）
Redis（短期缓存、限流计数或队列辅助，不能单独承担不可丢失的任务事实）
Metrics / Logs / Traces
Secret Manager / Credential Proxy
Audit Log
Alert Manager
```

## 3.2 模块职责

1. **API Gateway：** 身份认证、授权、速率限制、请求 ID、输入校验和统一错误格式。
2. **API Client：** 统一请求、超时、有限重试、流式响应处理、Token 用量解析和成本估算。
3. **Provider Adapter：** 封装供应商特有的请求格式、错误分类、Retry-After、Usage 和模型能力。
4. **Metrics Collector：** 采集请求数、成功率、延迟分位数、429/5xx 比率、Token、队列积压和资源指标。
5. **Scheduler：** 综合硬性保护规则、服务健康、预算、任务优先级、截止时间和资源状态做调度。
6. **Task Service：** 维护任务状态机、幂等键、租约、心跳、取消、超时和恢复逻辑。
7. **Budget Guard：** 对项目、任务、模型和时间窗口执行预算检查与预留。
8. **Agent Runtime：** 管理 Agent 的工具白名单、上下文边界、执行期限和审批点。
9. **Sandbox Manager：** 创建并销毁隔离执行环境，限制网络、文件、资源和系统调用。
10. **Credential Proxy：** 在受控服务端持有或获取密钥，Agent 不直接接触长期 Provider Key。
11. **Audit Service：** 记录高风险操作、权限检查、调度决策、审批和 Agent 工具调用。
12. **Dashboard / Alerting：** 展示运行状态、预算、队列、策略命中和异常告警。

## 3.3 建议技术栈

技术栈为建议项，可在技术评审后替换，不作为硬性需求：

- 后端：Python + FastAPI，或团队已有的成熟服务框架。
- 数据库：PostgreSQL，作为任务状态、配置和审计元数据的主要事实来源。
- 队列：MVP 可使用 PostgreSQL 持久化任务表与可靠轮询；需要更高吞吐后再引入专用消息队列。
- Redis：用于短期计数、缓存、分布式限流辅助或非权威状态；不可将仅存在 Redis 中的任务状态视为不可丢失。
- 监控：Prometheus + Grafana，或兼容的 Metrics / Logs / Traces 方案。
- 执行隔离：受限容器或专用微虚拟机；安全等级较高的代码执行任务优先考虑更强隔离边界。
- Secret Manager：云厂商密钥服务、Vault 或等价方案。
- 部署：Docker Compose 可用于本地开发；生产部署应使用受控的部署和密钥管理方案。

# 4. 功能需求

## 4.1 统一 API Client 与 Provider Adapter

### 必须实现

- 所有模型请求必须经过统一 API Client，业务模块不得各自直接调用供应商 SDK。
- 支持配置模型、超时、最大重试次数、请求优先级、任务 ID、幂等键和成本上限。
- 记录请求开始、结束、状态、耗时、模型、供应商、输入/输出 Token（若服务商提供）、重试次数和成本状态。
- 支持流式和非流式响应；流式请求中断时需记录已接收的用量信息（若可获得）。
- 统一错误分类，但保留供应商原始错误的受控引用，不能把未经脱敏的原始错误直接写入普通日志。
- 对未知错误采用保守处理，不因无法识别错误而无限重试。
- Provider Adapter 应能独立测试和升级。

### 推荐接口抽象

```python
class ProviderAdapter:
    def build_request(self, request):
        ...

    def classify_error(self, response_or_exception):
        ...

    def extract_usage(self, response):
        ...

    def extract_retry_after(self, response):
        ...

    def estimate_cost(self, usage, model, pricing_version):
        ...

    def get_capabilities(self, model):
        ...
```

以上为概念接口；具体类型、异步行为和异常定义应在详细设计阶段确定。

### 错误分类建议

- `AUTHENTICATION_ERROR`：凭据无效或认证失败。
- `PERMISSION_ERROR`：模型、项目或资源无权限。
- `RATE_LIMITED`：请求频率或配额限制。
- `PROVIDER_OVERLOADED`：供应商明确报告过载。
- `PROVIDER_SERVER_ERROR`：供应商 5xx 或等价服务端错误。
- `NETWORK_ERROR`：连接、DNS 或 TLS 等网络问题。
- `TIMEOUT_UNKNOWN`：请求超时，无法确认服务端是否已经处理。
- `INVALID_REQUEST`：请求格式或参数错误。
- `BUDGET_EXCEEDED`：预算限制。
- `CANCELLED`：请求或任务被取消。
- `UNKNOWN_ERROR`：无法可靠归类的错误。

## 4.2 请求监控与数据质量

### 采集指标

- 请求总数、成功数、失败数。
- 按供应商、模型、项目、任务类型统计的请求量。
- P50、P95、P99 延迟；样本量不足时不展示误导性的稳定分位数。
- HTTP 状态码和标准化错误分类分布。
- 429 比率、5xx 比率、超时率、重试率。
- 输入/输出 Token 与估算成本。
- 排队时间、任务等待时长、队列长度、Worker 利用率。
- 项目预算使用率和预算预留量。
- 数据缺失率、采集延迟、样本数和数据质量状态。

### 数据质量规则

- 所有聚合指标都应包含时间窗口、样本数和数据质量状态。
- 样本量不足时，标记为 `INSUFFICIENT_SAMPLE`，不得输出高置信度结论。
- 指标缺失不能默认视为零压力。
- 供应商维护窗口、平台自身故障和异常流量应可单独标记。
- 时间戳统一存储为 UTC；前端按用户时区显示。
- 对请求日志和指标定义去重键，避免消息重复消费导致统计重复累计。
- 区分观测值、估算值、预测值和供应商公开状态，不能混为一类数据。

## 4.3 压力评估与动态并发

### 决策优先级

```text
身份与安全限制
    >
预算硬上限与配额硬限制
    >
实时服务健康与熔断状态
    >
队列、Worker 与基础设施容量
    >
任务优先级和截止时间
    >
历史预测与软性评分
    >
成本优化偏好
```

### 硬性保护规则

- 认证失败：暂停对应凭据或 Provider 路径，禁止反复重试。
- 预算硬上限已达到：阻止新增可计费执行；已运行任务按配置安全结束或中止。
- 连续 429：根据供应商响应和配置进入退避，必要时触发熔断。
- 5xx 或网络故障持续发生：有限重试并执行熔断策略。
- 调度依赖不可用或关键指标质量不足：使用预设保守并发上限，不得自动放宽。
- Worker、数据库或沙箱资源不足：暂停低优先级任务，不得仅因 API 压力低就启动更多 Agent。
- 任务已过期或被取消：不得继续启动新 Attempt。

### 软性评分

压力分数可以作为调度辅助，但不能成为唯一依据。应避免对高度相关的请求量、延迟、429、重试率和队列长度重复计权。

建议 MVP 采用“硬规则 + 有限阈值 + 简单评分”。每个评分必须记录：
- `sample_count`
- `data_quality`
- `confidence`
- `policy_version`
- `reason_codes`

并通过离线回放或影子模式验证后，才允许影响真实调度。

### 动态并发要求

- 设定全局、供应商、模型、项目和任务类型级别的并发上限。
- 并发调整设置最小值、最大值、调整步长、冷却时间和恢复条件。
- 降低并发可以快速执行；恢复并发应更谨慎，避免振荡。
- 不允许并发自适应越过管理员设置的硬上限。
- 并发策略每次变更都必须记录旧值、新值、原因和策略版本。

## 4.4 限流、退避与熔断

- 对 429 优先遵守供应商提供的 `Retry-After` 或等价信息；若不存在，使用指数退避与随机抖动。
- 重试次数、总重试时间和总成本均需设置上限。
- 对明显不可重试的 4xx（如无效参数、权限错误）不自动重试。
- 对认证错误优先停止请求并告警，不得反复尝试同一失效密钥。
- 熔断器应具备 `CLOSED`、`OPEN`、`HALF_OPEN` 等状态。
- 熔断恢复通过有限探测请求进行，不允许大量任务同时试探。
- 不同 Provider、模型和项目的熔断状态应按明确的隔离维度维护。
- 熔断打开、半开、关闭都应产生事件与审计记录。
- 取消请求后应尽可能停止本地工作；如果上游无法取消，必须记录可能仍在执行或计费的风险。

## 4.5 任务队列与状态机

### 任务状态

```text
PENDING
QUEUED
CLAIMED
RUNNING
WAITING_EXTERNAL_RESULT
RETRY_WAIT
PAUSED
REVIEW_REQUIRED
SUCCEEDED
FAILED
CANCELLED
EXPIRED
UNKNOWN
```

### 状态语义

- `PENDING`：任务已创建，尚未进入可执行队列。
- `QUEUED`：满足基本条件，等待调度。
- `CLAIMED`：Worker 已领取任务并持有有效租约。
- `RUNNING`：执行已开始。
- `WAITING_EXTERNAL_RESULT`：正在等待外部 API、Git 或其他系统确认结果。
- `RETRY_WAIT`：符合重试条件，等待退避时间结束。
- `PAUSED`：被策略或人工暂停。
- `REVIEW_REQUIRED`：需要人工判断或审批。
- `SUCCEEDED`：任务完成且结果已持久化。
- `FAILED`：已确认失败且不再自动重试。
- `CANCELLED`：任务被取消；外部副作用是否已发生需单独记录。
- `EXPIRED`：任务超过有效期或截止时间。
- `UNKNOWN`：无法确认执行结果或外部副作用状态，必须先查询、对账或人工处理。

### 一致性与恢复

- 每个逻辑任务拥有 `task_id`；每次执行拥有 `execution_id`；每次尝试拥有 `attempt_id`。
- 创建任务 API 支持 `Idempotency-Key`，同一键在有效期内重复提交不得创建重复任务。
- Worker 领取任务时获取带过期时间的租约，并定期发送心跳。
- 任务状态转换必须由数据库事务或等效的原子机制保护。
- 使用事务发件箱（Transactional Outbox）或等效可靠机制，避免数据库提交成功但事件未发布造成状态丢失。
- 队列消息允许至少一次投递；消费者必须幂等。
- 租约过期后，先检查上次执行记录和外部副作用状态，不得立即盲目重试。
- 对已创建 PR、已发送消息、已触发部署等外部副作用，必须查询目标系统或使用对端幂等机制。
- 无法确认结果时进入 `UNKNOWN`，提供人工处理入口。
- 任务取消应记录取消请求时间、确认状态和可能的残余外部执行。
- 任务必须支持最大执行时长、最大 Attempt 数和最大累计成本。

### 建议字段

```text

attempt_id
idempotency_key
tenant_id
project_id
environment
status
attempt_no
lease_id
worker_id
created_at
started_at
heartbeat_at

finished_at

cost_status

```

## 4.6 重试与外部副作用

请求重试前必须判定操作类型：

1. **只读或纯推理请求：** 可在限定次数、时间和成本内重试；仍可能发生重复计费。
2. **带外部副作用的请求：** 如发送消息、写入数据、创建 PR、部署或触发工作流；必须有幂等键、对端查询或去重方案。
3. **结果不确定的请求：** 如客户端超时但服务端可能已完成；先查询状态或进入 `UNKNOWN`，不得直接按普通失败处理。

每次 Attempt 都要记录请求 ID、开始与结束时间、错误分类、重试原因、是否可能计费和累计成本。

## 4.7 预算与成本治理

### 预算层级

- 全平台预算。
- Provider / 模型预算。
- 项目预算。
- 单任务预算。
- 单次执行预算。
- 可选的日、周、月滚动预算。

### 预算检查

- 在任务入队、开始执行和每次重试前检查预算。
- 对可能发生的成本进行预算预留，防止多个并发任务同时通过检查而共同突破预算。
- 对流式请求或长任务，按可获得的用量信息更新成本；无法实时获得用量时使用保守估算。
- 设置软告警阈值和不可自动突破的硬上限。
- 硬上限达到后阻止新的可计费执行，并按配置安全处理已运行任务。
- 预算调整必须审计；生产预算上调应有审批。

### 成本状态

```text
estimated
actual
unknown
reconciled
```

每笔成本记录至少关联：
- Provider、模型和计价版本。
- 输入/输出 Token 或可获得的计费单位。
- 请求与 Attempt ID。
- 估算依据和计价生效时间。
- 数据来源与对账状态。

### 对账要求

- 定期导入供应商账单或可用的官方用量数据。
- 区分平台估算值与供应商实际账单，不将估算值展示为精确账单。
- 记录对账差异、币种、税费处理口径和计价版本。
- 若供应商不提供账单 API，允许受控的人工导入流程。
- 账单对账失败不得自动放宽预算。

## 4.8 历史分析与预测

预测功能应在基础监控运行稳定且数据质量达标后启用。

### 可预测目标

- 本平台自身的请求量和任务到达率。
- 本平台观察到的响应延迟、429 比率和失败率趋势。
- 本平台队列积压和 Worker 资源需求。
- 低优先级任务的推荐启动时间。

### 不可声称的预测

- 供应商真实内部负载或全局用户流量。
- 未公开的剩余容量或确定可用配额。
- 没有证据支持的“某时段一定不会限流”。

### 最小要求

- 明确预测窗口、训练数据范围、样本量、置信度和数据质量。
- 处理节假日、服务维护、数据缺失和异常值。
- 采用时间序列切分进行回测，避免未来数据泄漏。
- 与简单基线比较，不因使用复杂模型就默认更准确。
- 先使用影子模式，仅记录推荐结果而不控制真实调度。
- 只有通过离线回测、影子观察和人工审核后，才能影响低优先级任务的启动时间或排序。
- 预测不能覆盖安全规则、实时熔断和预算硬上限。

## 4.9 Agent 自动化任务

### 分阶段开放

1. 只读分析和问题归纳。
2. 文档与测试用例生成。
3. 在隔离环境中执行测试。
4. 修改非生产代码并生成补丁。
5. 创建分支和 Pull Request。
6. 人工审核后合并。
7. 生产部署继续由独立审批流程控制。

MVP 默认只开放前两至三项，代码修改能力需在沙箱安全验收通过后开放。

### Agent 工具白名单

每个任务必须显式声明允许使用的工具，例如：
- 读取指定仓库中的授权文件。
- 在隔离工作目录内编辑文件。
- 执行白名单测试命令。
- 查询只读的构建或测试结果。
- 创建指定仓库中的非保护分支。
- 提交 Pull Request 草稿。

默认禁止：
- 任意 shell 命令或不受控的特权命令。
- 访问宿主机敏感路径。
- 修改平台权限、审计、安全策略或预算硬上限。
- 读取其他项目、其他任务或其他租户的数据。
- 直接合并主分支、发布生产版本或执行破坏性数据库操作。
- 将代码、日志、Prompt 或密钥发送到未批准的外部地址。

### Prompt Injection 与不可信内容

- 仓库代码、README、Issue、日志、网页、第三方文档和模型输出均视为不可信数据。
- 不可信内容不得覆盖系统策略、授权配置或工具白名单。
- Agent 不得因文件中的指令而扩大权限、读取额外文件或绕过审批。
- 工具执行权限必须由外部策略引擎校验，而不是仅依赖模型自我约束。
- 工具参数必须经过结构化 Schema 校验、路径规范化和权限检查。
- 对高风险命令使用显式允许列表，不能只用黑名单。
- 输出补丁应执行 Secret Scan、依赖扫描和适用的静态分析。
- 检测到密钥泄露、权限绕过或疑似外传行为时，停止任务、隔离工作区并告警。

# 5. 安全需求

## 5.1 Agent 沙箱与执行隔离

**安全边界不能只由配置项声明，必须通过实际隔离机制和负向测试验证。**

最低要求：
- Worker 与 Agent 以非 root 身份运行。
- 禁止 privileged 容器和 Docker Socket 挂载。
- 禁止挂载宿主机根目录、生产配置目录、SSH 私钥目录和其他用户 Home 目录。
- 每个任务使用独立、权限受限的工作目录；高风险任务使用独立容器或微虚拟机。
- 使用 seccomp、AppArmor、SELinux 或同等机制限制系统调用和访问。
- 限制 CPU、内存、磁盘、进程数、文件描述符和执行时长。
- 默认关闭出站网络；确有依赖下载需求时，使用受控代理和域名/目的地白名单。
- 阻止访问云平台元数据服务、宿主机管理端口和内网敏感服务。
- 不向 Agent 继承宿主机完整环境变量。
- 任务结束后销毁执行环境；缓存需隔离并定期清理。
- Git Hook 默认禁用；依赖版本锁定，并对新增依赖执行审核与扫描。
- 不能仅凭容器隔离宣称能抵御所有内核漏洞；高风险不可信代码应考虑更强的隔离方案。

## 5.2 密钥与凭据管理

- Provider API Key 存放在 Secret Manager 或受控凭据服务中。
- Agent 默认不得直接读取长期 Provider Key。
- 模型调用通过 Credential Proxy / API Gateway 完成，代理只暴露必要的调用能力。
- 凭据按 Provider、项目、环境和用途隔离，支持轮换、吊销和过期。
- 不通过命令行参数、Prompt、普通日志、错误堆栈或任务报告传递密钥。
- Worker 只获得短期、范围受限的授权；不允许继承无关环境变量。
- Git 凭据使用独立机器人身份和最小仓库权限，禁止组织级广泛权限。
- 记录凭据访问的主体、时间、用途和结果，但不记录凭据明文。
- 怀疑凭据泄露时，支持立即吊销、轮换和关联任务暂停。

## 5.3 Webhook 安全

- 使用 HMAC 签名或等效认证机制。
- 签名应覆盖时间戳、唯一事件 ID 和原始请求体。
- 验证时间戳有效窗口并防止重放。
- 使用常量时间方式比较签名。
- 限制请求体大小、内容类型和处理时长。
- 可根据部署条件增加 IP 白名单或 mTLS，但不能将 IP 白名单作为唯一认证方式。
- Webhook 失败重试必须有上限和退避。
- 日志中不得包含敏感载荷。
- 接收端需要对重复事件进行幂等处理。

推荐请求头示例：

```text
X-Webhook-Id
X-Webhook-Timestamp
X-Webhook-Signature
```

## 5.4 管理端与 API 安全

- 所有管理接口实施服务端授权检查。
- 对登录、任务创建、策略变更和敏感读取实施速率限制。
- Web 管理端启用 HTTPS、安全 Cookie、会话过期和 CSRF 防护。
- 对用户输入、模型输出和日志内容进行适当的输出编码，避免 XSS。
- 使用参数化数据库查询，避免 SQL 注入。
- 高风险操作显示变更差异、影响范围和回滚方案。
- 对预算上调、权限扩大、生产部署和安全策略变更实施审批。
- 管理员和审核者分离；关键操作支持双人复核。
- 对所有鉴权失败、越权尝试和异常管理操作生成安全事件。

## 5.5 供应链安全

- 使用依赖锁定文件和可信软件源。
- 对新增依赖执行漏洞、许可证和来源检查。
- 禁止自动执行未经审核的安装脚本。
- 限制包管理器网络访问；构建时优先使用受控镜像或缓存。
- 记录依赖变化、构建来源和构建产物摘要。
- Git Hook 默认禁用。
- 关键依赖升级必须经过测试和审核。
- 对代码修改执行 Secret Scan、静态分析、依赖漏洞扫描和测试。

## 5.6 日志、隐私与数据保留

建议数据分级：

| 等级 | 示例 | 要求 |
|---|---|---|
| L1：运行元数据 | 时间、耗时、状态码、请求 ID | 可按运营需要保留，限制访问 |
| L2：业务元数据 | 项目、模型、任务类型、Token 用量 | 项目权限隔离 |
| L3：上下文与错误详情 | Prompt 摘要、代码片段、错误上下文 | 默认不完整保存；脱敏、限权、限期 |
| L4：秘密与高敏数据 | API Key、密码、私钥、个人敏感信息 | 禁止进入普通日志、指标标签和告警载荷 |

要求：
- 默认不保存完整 Prompt 和完整模型响应；如业务确需保存，必须显式启用、说明目的并配置保留期限。
- 日志中禁止记录密钥、Authorization Header、Cookie 和未经脱敏的敏感请求体。
- 对用户输入、模型输出和异常内容执行敏感信息检测。
- 设置日志保留、归档、删除、导出和访问审计流程。
- 指标标签不得使用高基数或敏感内容，例如完整 Prompt、用户邮箱或原始 URL 查询参数。
- 数据跨境、个人信息处理和合规要求需根据实际部署地域及业务进行单独评估，不能仅凭本技术文档视为已合规。

# 6. 数据模型与事件规范

## 6.1 核心数据实体

建议至少包含：

- `projects`：项目与隔离配置。
- `users`、`roles`、`role_bindings`：身份与授权。
- `provider_configs`：供应商和模型配置元数据，不保存明文密钥。
- `tasks`：逻辑任务与当前状态。
- `task_executions`：任务执行实例。
- `task_attempts`：单次尝试和调用结果。
- `api_request_logs`：请求元数据与成本估算。
- `budget_accounts`、`budget_reservations`、`cost_records`：预算、预留和成本账本。
- `scheduler_decisions`：调度输入摘要、规则命中和策略版本。
- `policy_versions`：调度与安全策略版本。
- `approvals`：审批请求和决定。
- `audit_events`：安全与管理审计。
- `outbox_events`：待可靠发布的事件。
- `provider_billing_records`：供应商账单导入与对账结果。

## 6.2 错误信息存储

业务数据库优先保存：
- `error_code`
- `error_category`
- `safe_error_message`
- `raw_error_reference`

原始错误仅能存放于受控日志系统，执行脱敏、访问控制和保留策略。不能将原始异常全文直接放入普通任务表。

## 6.3 统一事件模型

事件建议包含：

```json
{
  "event_id": "unique-event-id",
  "event_type": "RateLimitDetected",
  "event_version": "v1",
  "occurred_at": "2026-01-01T00:00:00Z",
  "source": "api-client",
  "tenant_id": "tenant-id",
  "project_id": "project-id",
  "task_id": "task-id",
  "execution_id": "execution-id",
  "trace_id": "trace-id",
  "payload": {}
}
```

建议事件类型包括：
- `ApiRequestStarted`
- `ApiRequestCompleted`
- `ApiRequestFailed`
- `RateLimitDetected`
- `CircuitBreakerOpened`
- `CircuitBreakerHalfOpened`
- `CircuitBreakerClosed`
- `TaskCreated`
- `TaskQueued`
- `TaskClaimed`
- `TaskStarted`
- `TaskPaused`
- `TaskRetried`
- `TaskSucceeded`
- `TaskFailed`
- `TaskUnknown`
- `AgentExecutionStarted`
- `AgentExecutionFinished`
- `BudgetThresholdReached`
- `ApprovalRequired`
- `PolicyChanged`

事件消费者必须支持重复投递；事件 Schema 需版本化。

## 6.4 调度决策记录

每次决策至少记录：
- `decision_id`
- 关联的任务或调度周期。
- 决策结果，如 `ALLOW`、`DELAY`、`PAUSE`、`REJECT`、`REVIEW_REQUIRED`。
- `reason_codes`
- 关键输入指标摘要、样本数和数据质量。
- 使用的 `policy_version`
- 决策时间。
- 旧值与新值（如调整并发）。
- 是否由人工覆盖以及覆盖理由。

不得在决策日志中保存完整密钥、完整 Prompt 或不必要的个人信息。

# 7. 配置管理与策略回滚

所有会影响生产行为的配置必须版本化，包括：
- Provider / 模型白名单。
- 并发上限与限流参数。
- 429 退避和熔断阈值。
- 预算阈值。
- 任务优先级与截止时间规则。
- Agent 工具白名单和沙箱策略。
- 数据保留和日志脱敏规则。
- 告警规则。
- 模型价格表。

每个配置版本应包含：
- `config_id`
- `version`
- `created_by`
- `approved_by`（适用时）
- `created_at`
- `effective_at`
- `change_reason`
- `previous_version`
- `rollback_supported`

生产配置变更流程：
1. 提交变更。
2. 显示差异与影响范围。
3. 执行静态校验和策略测试。
4. 需要时进行审批。
5. 灰度或分阶段生效。
6. 观察指标。
7. 异常时回滚到已知安全版本。
8. 记录完整审计事件。

禁止 Agent 自行修改安全策略、预算硬上限或自身权限。

# 8. API 设计要求

## 8.1 通用约定

- 使用版本化 API 路径，例如 `/api/v1/...`。
- 所有请求和响应应关联 `request_id`；异步任务还应包含 `task_id`、`execution_id` 和 `trace_id`。
- 列表接口支持分页、过滤和明确的排序规则。
- 创建任务接口支持 `Idempotency-Key`。
- 所有接口执行认证、授权、输入校验和速率限制。
- 错误响应不得暴露堆栈、密钥、内部路径或数据库连接信息。
- 对外 API 应定义超时、重试语义、兼容性和废弃策略。

## 8.2 统一错误格式

```json
{
  "code": "TASK_BUDGET_EXCEEDED",
  "message": "任务预算已达到限制",
  "request_id": "request-id",
  "task_id": "task-id",
  "retryable": false,
  "details": {},
  "timestamp": "2026-01-01T00:00:00Z"
}
```

`details` 只能包含经过授权且不敏感的诊断信息。

## 8.3 建议 API 端点

| 方法 | 端点 | 用途 |
|---|---|---|
| POST | `/api/v1/tasks` | 创建任务，支持幂等键 |
| GET | `/api/v1/tasks/{task_id}` | 查询任务状态 |
| POST | `/api/v1/tasks/{task_id}/cancel` | 请求取消任务 |
| POST | `/api/v1/tasks/{task_id}/retry` | 请求重试；服务端必须验证可安全重试 |
| GET | `/api/v1/tasks/{task_id}/events` | 查询授权范围内的任务事件 |
| GET | `/api/v1/metrics/summary` | 查询聚合指标 |
| GET | `/api/v1/budgets` | 查询授权范围内的预算 |
| POST | `/api/v1/approvals/{approval_id}/decision` | 提交审批决定 |
| GET | `/api/v1/policies` | 查看有权访问的策略版本 |
| POST | `/api/v1/policies/{policy_id}/proposals` | 提交策略变更提案 |

端点为建议设计，具体请求 Schema、响应 Schema、状态码和权限矩阵应在接口设计阶段补齐。

# 9. 告警与运维

## 9.1 告警类型

- 429 比率或连续限流超过阈值。
- 5xx、超时或错误率持续升高。
- Provider 熔断打开。
- 预算达到软阈值或硬上限。
- 队列等待时间过长或任务饥饿。
- Worker、数据库、队列或沙箱资源异常。
- 任务进入 `UNKNOWN`。
- 密钥认证失败或疑似泄露。
- Agent 尝试越权、读取敏感路径或访问未批准网络。
- 审计、指标或成本数据采集异常。
- 供应商账单对账差异超过阈值。

## 9.2 告警要求

- 告警需包含严重级别、触发条件、时间窗口、影响范围、建议动作和关联事件 ID。
- 告警载荷不得包含密钥、完整 Prompt 或敏感代码。
- 同一故障应支持去重、合并、静默窗口和恢复通知。
- 对无法自动恢复的高风险告警，必须提供人工接管流程。
- Webhook 通知失败应有限重试，并提供可观测的失败状态。

---

# 10. 非功能需求

以下数值是建议的初始验收目标，应根据预期负载和部署条件在技术评审后确认。

## 10.1 性能与容量

- 对平台内部的普通读 API，目标 P95 延迟小于 300 ms（不含外部模型响应）。
- 创建任务接口应快速返回任务 ID，不应同步等待长时间 Agent 执行。
- API 请求监控与任务执行采用异步处理，避免日志或报表影响请求主链路。
- 系统应支持通过压测确认的目标吞吐量；在需求确认前不虚构固定 QPS 容量。
- 指标、日志和任务表必须有索引、归档与容量增长规划。

## 10.2 可用性与恢复

- MVP 应定义服务目标、维护窗口和故障等级。
- 任务状态的权威记录应持久化于事务数据库或等效持久存储。
- Redis 或消息队列短暂故障时，系统应进入明确的降级状态，不应静默丢失任务。
- 定义 RPO（最大可接受数据丢失窗口）和 RTO（目标恢复时间），在部署方案确定后给出数值。
- 定期进行备份恢复演练。
- 恢复后核查 `RUNNING`、过期租约和 `UNKNOWN` 任务，禁止盲目重放全部任务。

## 10.3 可观测性

- 使用统一 `request_id`、`trace_id`、`task_id` 和 `execution_id` 关联日志与事件。
- 监控平台本身的错误率、延迟、队列积压、数据库连接池和资源使用率。
- 指标缺失、采集延迟和日志写入失败本身也应可观测。
- 不在指标标签中存放高基数或敏感值。

## 10.4 可维护性

- Provider Adapter、调度策略和 Agent 工具应模块化。
- 关键策略具有单元测试、集成测试和回归测试。
- 数据库 Schema 和事件 Schema 需版本管理。
- 配置应可校验、可追踪、可回滚。
- 所有关键依赖和运行时版本应锁定并记录。

# 11. MVP 范围与实施路线

## 阶段 0：设计与安全基线

交付：
- 威胁建模与数据流图。
- 权限矩阵。
- API 与任务状态机设计。
- Provider Adapter 契约。
- 日志脱敏与数据保留策略。
- 沙箱技术验证。
- 预算与幂等机制设计。

退出条件：技术评审通过；明确部署边界、凭据方案和高风险操作审批流程。

## 阶段 1：统一调用与可观测性

交付：
- 单一 Provider（先以 DeepSeek 为例）的统一 API Client。
- 请求日志、指标采集、基础 Dashboard。
- 错误分类、Token 与估算成本统计。
- 基础认证、授权和密钥代理。
- 配置版本管理的最小实现。

退出条件：所有模型请求均经过统一入口；日志脱敏测试通过；请求和成本统计可追踪。

## 阶段 2：可靠任务队列与规则调度

交付：
- 持久化任务表、任务状态机、租约与心跳。
- 幂等创建、重复消息去重和恢复逻辑。
- 429 退避、有限重试、熔断。
- 并发上限、队列优先级、预算硬上限。
- 调度决策记录与告警。

退出条件：故障注入测试通过；状态不确定时不会盲目重试；预算硬上限不能被并发竞争突破。

## 阶段 3：历史分析与影子预测

交付：
- 数据质量评估、小时/日聚合。
- 历史基线、异常检测和预测回测。
- 影子模式下的调度建议和效果报告。

退出条件：预测在明确数据集上优于或合理匹配简单基线；未通过评估的预测不控制生产调度。

## 阶段 4：受限 Agent

交付：
- 只读分析、文档与测试生成。
- 真实隔离的执行环境。
- 工具白名单、审计、Secret Scan 和人工审批。
- 在授权仓库创建分支与 PR 草稿。

退出条件：沙箱负向测试、越权测试和密钥泄露测试通过；生产合并与发布仍需人工审批。

## 阶段 5：多 Provider 与策略优化

交付：
- 新 Provider Adapter。
- 模型能力与成本兼容性检查。
- 受控的模型回退策略。
- 公平调度、任务 aging 和策略对照实验。

退出条件：每个 Provider 均通过独立契约测试；切换模型不会绕过数据分类、预算和输出 Schema 约束。

# 12. 测试与验收标准

## 12.1 API 与调度测试

必须覆盖：
- 正常请求、流式响应和非流式响应。
- 429、5xx、超时、连接失败、无效请求和认证失败。
- `Retry-After` 存在与缺失的情况。
- 并发请求竞争预算预留。
- 全局、模型和项目级并发上限。
- 熔断打开、半开和恢复。
- 队列积压、任务过期和低优先级任务饥饿。
- Provider Adapter 返回未知格式或缺失 Usage。
- 指标采集延迟、样本不足和数据缺失。
- 成本估算与官方账单对账。

验收要求：
- 不可重试错误不会进入无限重试。
- 每个重试都有可追踪的原因和成本记录。
- 预算硬上限不会因并发竞争而被系统主动突破。
- 关键指标缺失时采用保守策略。
- 调度决策可以解释并定位到策略版本。

## 12.2 一致性与恢复测试

必须覆盖：
- 同一 `Idempotency-Key` 重复创建任务。
- 消息重复投递。
- 数据库提交成功但事件发布失败。
- Worker 在领取任务后崩溃。
- Worker 在外部请求成功后、状态落库前崩溃。
- 租约过期与心跳丢失。
- 调度器重启和数据库短暂不可用。
- 任务取消与外部请求仍在执行的竞争。
- Git PR 已创建但客户端未收到响应。
- 结果无法确认时进入 `UNKNOWN` 并触发处理流程。

验收要求：
- 状态变化持久化且可追踪。
- 重复投递不会重复创建逻辑任务。
- 外部副作用不确定时不会直接盲目重试。
- 系统重启后能区分可安全恢复任务和需要人工确认的任务。

## 12.3 Agent 安全测试

必须覆盖：
- 尝试读取 Provider Key、环境变量和 Secret Manager。
- 尝试访问宿主机文件、Docker Socket 和其他任务目录。
- 尝试访问云平台元数据、内网管理端口和未批准域名。
- 仓库中存在要求忽略规则或外传数据的恶意文本。
- Agent 尝试修改权限、预算、安全策略或审批流程。
- Agent 尝试绕过审批、合并主分支或发布生产版本。
- 恶意依赖、安装脚本和 Git Hook。
- CPU、内存、磁盘、进程数和运行时长超限。
- Secret Scan 检测到密钥后停止任务并告警。

验收要求：
- 危险操作被执行环境或服务端策略阻止，而不是仅依赖模型拒绝。
- 触发的安全事件有审计记录和告警。
- 测试中不得出现密钥泄露或跨项目数据读取。
- 任务超限后可终止并清理资源。

## 12.4 权限与 Web 安全测试

- 只读用户不能修改策略。
- 开发者不能读取明文 API Key。
- 项目管理员不能读取其他项目数据。
- 审核者不能批准自己发起的变更。
- 无效、过期或被吊销的会话不能执行管理操作。
- Webhook 错误签名、过期时间戳和重复事件被拒绝或幂等处理。
- 对常见注入、XSS、CSRF、越权访问和请求体过大场景进行测试。

## 12.5 可运营性测试

- 数据库备份可恢复。
- 关键服务停止后能触发告警。
- 日志写入失败不会导致主请求无限阻塞。
- 预算、限流和熔断状态在仪表盘中可见。
- 配置变更可审计并可回滚。
- RPO/RTO 在演练中得到验证。

6. 任务状态机和事件 Schema 文档。

9. Docker/部署配置及生产环境安全说明。
10. 监控 Dashboard 与告警规则。
11. 配置变更、备份恢复和回滚手册。
12. 威胁模型、权限矩阵和数据保留说明。
13. 已知限制、未完成项和后续路线图。
14. 不得提交真实密钥、生产数据或未经授权的第三方凭据。

# 14. 已知风险与待确认决策

以下内容不能在缺少业务输入时擅自假设，应在开发启动前确认：

- 目标用户数量、并发量和请求吞吐目标。
- 首期部署位置、云环境、网络边界和数据驻留要求。
- 是否为单租户内部工具，还是未来面向多个组织提供服务。
- 首期需要支持的 Provider、模型和接口类型。
- 预算币种、价格来源、硬上限策略和账单对账方式。
- 任务优先级定义、截止时间语义和取消策略。
- Agent 首期允许读取和修改的仓库范围。
- 沙箱采用容器还是微虚拟机，以及允许的网络访问范围。
- RPO、RTO、备份频率和日志保留期限。
- 生产部署、代码合并、数据库变更的审批责任人。
- 合规要求，包括个人信息、数据跨境、代码保密和供应商数据处理条款。

若这些内容尚未确认，应在配置中显式标记为待定，并采用安全默认值，不得由开发 Agent 自行作出会扩大权限或成本的决定。

# 15. 最终硬性规则

以下规则不可被普通任务配置、历史预测或 Agent 自主决策覆盖：

1. 所有模型请求必须经过统一 API Client。
2. 所有任务必须有唯一 ID、幂等机制和可追踪的执行记录。
3. 状态不确定时不得无条件重试。
4. 所有重试必须受次数、时间和成本限制。
5. Agent 不得直接持有生产环境长期密钥。
6. Agent 不得访问 Docker Socket、宿主机敏感目录或云平台元数据服务。
7. Agent 只能访问任务明确授权的仓库、分支、目录和工具。
8. 仓库内容、Issue、日志、网页和模型输出均视为不可信输入。
9. Agent 不得因不可信内容而扩大权限或绕过审批。
10. 生产代码合并、部署、权限变更和破坏性数据库操作默认需要人工审批。
11. 预算硬上限不得被自动突破。
12. 预测结果不得覆盖实时服务状态、权限和安全限制。
13. 所有高风险操作必须审计。
14. 所有 Webhook 必须认证、签名验证并防重放。
15. 所有配置变更必须版本化；生产变更需按风险审批并支持回滚。
16. 敏感数据不得进入普通日志、指标标签和告警载荷。
17. 系统重启后，无法确认结果的任务必须进入 `UNKNOWN` 或等效的人工核查流程。
18. 多模型切换必须检查能力、输出格式、成本和数据安全兼容性。
19. 关键安全控制失效时，应暂停高风险操作，而不是默认放行。
20. 任何“自动化成功”都必须有可验证的执行结果，不能只依赖 Agent 自述。

# 16. 结论

NexusAI 的合理演进路径是：

```text
统一调用与监控
    -> 可靠任务队列
    -> 规则调度、限流、熔断和预算治理
    -> 历史分析与影子预测
    -> 隔离环境中的受限 Agent
    -> 多 Provider 与更高级的自动化
```

首期交付的成功标准不是“系统看起来足够智能”，而是能够回答并验证以下问题：

- 每个请求发生了什么？
- 为什么调度器允许、延迟或拒绝一个任务？
- 发生超时后，系统是否知道请求可能已经执行？
- 预算是否能在并发情况下被可靠保护？
- Worker 崩溃后，任务能否安全恢复？
- Agent 是否被技术边界限制，而非仅靠 Prompt 约束？
- 出现事故后，是否能追踪、止损、恢复和回滚？

只有先建立这些闭环，再引入预测和 Agent 自动化，平台才具备可维护、可审计和逐步进入生产环境的基础。
